# PART 1 — INTELLIGENCE ARCHITECTURE

## 1. Purpose

The AI Intelligence Engine transforms a validated task into an optimized institutional research strategy.

It determines:

- what should be researched
- which analytical capabilities are required
- which modules should participate
- which frameworks should be applied
- how deeply the topic should be analyzed
- what deliverables should be produced

The Intelligence Engine performs strategic planning only.

It never performs research, reasoning, execution, auditing, or output generation.

## 2. Vision

Enable the AI Operating System to think before it acts.

Every validated user request should produce an adaptive research strategy rather than a fixed workflow.

Planning must remain:

- dynamic
- explainable
- registry-driven
- scalable
- evidence-aware
- future-proof
- auditable
- model-agnostic

## 3. Design Philosophy

The Intelligence Engine follows six guiding principles.

### Principle 1 — Understand before planning
Never build a research plan until the user's objective is fully understood.

### Principle 2 — Plan before execution
Research begins only after an optimized execution strategy has been approved.

### Principle 3 — Dynamic over static
Never rely on hard-coded modules, frameworks, or workflows. All selections must be discovered dynamically.

### Principle 4 — Minimum effective intelligence
Select only the capabilities required to solve the current objective.

### Principle 5 — Institutional planning
Research plans should resemble the workflow of a professional investment research organization rather than an individual analyst.

### Principle 6 — Adapt continuously
Plans may evolve when evidence, objectives, dependencies, or runtime conditions change.

## 4. Responsibilities

The Intelligence Engine shall:

- interpret validated user objectives
- determine research intent
- classify task type
- estimate complexity
- determine research depth
- select research mode
- generate execution strategy
- request candidate modules
- request analytical frameworks
- estimate planning cost
- build the ResearchPlanObject
- provide strategic guidance to the Execution Engine

## 5. Non-Responsibilities

The Intelligence Engine shall never:

- execute modules
- manage runtime state
- allocate context
- perform valuation
- perform technical analysis
- generate investment recommendations
- perform quality audits
- generate final outputs
- store permanent knowledge
- hard-code module names
- hard-code framework names

These responsibilities belong to dedicated engines and registries.

## 6. Core Principles

Every planning decision must satisfy:

- relevance
- efficiency
- scalability
- explainability
- traceability
- determinism
- adaptability
- institutional quality
- transparency
- consistency

# PART 2 — INTELLIGENT PLANNING

## 9. Intent Understanding

The Intelligence Engine identifies the user's actual objective.

Supported intent categories include:

- learn
- discover
- research
- analyze
- compare
- evaluate
- screen
- value
- monitor
- review
- portfolio
- risk
- strategy
- education

Multiple intents may exist.

The system shall determine:

- Primary Intent
- Secondary Intent(s)
- Supporting Intent(s)

Planning decisions prioritize the Primary Intent.

## 10. Task Classification

Convert user intent into executable research tasks.

Supported task types include:

- Educational Explanation
- Company Research
- Sector Research
- Industry Research
- Stock Screening
- Financial Analysis
- Technical Analysis
- Valuation
- Investment Thesis
- Risk Assessment
- Portfolio Review
- Watchlist Monitoring
- Annual Report Analysis
- Quarterly Result Analysis
- Macro Analysis
- Multi-Company Comparison
- Investment Committee Review

Tasks remain independent from specific modules.

No hard-coded workflow definitions are permitted.

## 11. Research Mode Selection

Research Mode defines the operating style of the entire research session.

Available modes include:

- Quick Answer
- Exploration
- Discovery
- Focused Research
- Deep Research
- Institutional Research
- Validation
- Monitoring
- Portfolio Review
- Learning

Selection depends upon:

- user intent
- task type
- research complexity
- expected deliverables
- available evidence
- execution cost
- time sensitivity

Only one Primary Research Mode may exist.

Additional modes may support the primary mode.

## 12. Complexity Assessment

Estimate planning complexity before selecting resources.

Complexity levels:

### Level 1 — Simple
Basic educational questions and single-metric interpretation.

### Level 2 — Standard
Single-company analysis, basic screening, or sector overview.

### Level 3 — Advanced
Comprehensive company research, valuation, investment thesis, or risk assessment.

### Level 4 — Institutional
Portfolio construction, multi-company comparison, capital allocation, or investment committee work.

Complexity determines:

- research depth
- module count
- framework count
- validation level
- expected runtime
- context budget
- explanation depth

## 13. Research Depth Selection

Determine how deeply the system should investigate.

Available depth levels:

- Quick
- Standard
- Comprehensive
- Institutional

Selection factors:

- task complexity
- research mode
- evidence availability
- expected output
- execution budget
- risk level

The selected depth becomes part of the ResearchPlanObject.

## 14. Planning Cost Estimation

Estimate execution requirements before runtime.

Metrics:

- Estimated Context Cost
- Estimated Module Count
- Estimated Framework Count
- Estimated Runtime
- Estimated Computational Cost
- Expected Confidence Ceiling
- Expected Research Coverage

The Execution Engine uses these estimates for optimization.

Cost estimation is directional, not absolute. It supports planning decisions and resource allocation, but it does not replace runtime measurement.

## 15. Intelligence Validation

Before approving a Research Plan verify:

- user intent identified
- task classified
- research mode selected
- complexity estimated
- research depth selected
- cost estimated
- deliverables identified
- planning constraints recorded
- registry compatibility checked
- dependency requirements captured

Only validated plans may proceed to dynamic intelligence planning.

# PART 3 — DYNAMIC INTELLIGENCE

## 16. Dynamic Module Selection

### Purpose

Select the minimum set of modules required to accomplish the user's objective.

The Intelligence Engine never hard-codes module names.

All module discovery occurs through the AI Module Registry.

### Module Discovery Inputs

- Primary Intent
- Task Type
- Research Mode
- Research Depth
- Industry
- Sector
- Company
- Investment Style
- Output Type
- Execution Constraints

### Module Discovery Process

```text
User Objective
↓
Generate Search Criteria
↓
Query Module Registry
↓
Receive Candidate Modules
↓
Filter Compatible Modules
↓
Remove Duplicates
↓
Rank Modules
↓
Return Module Stack
```

### Module Selection Rules

Every selected module must satisfy:

- registered
- production ready
- compatible version
- trigger conditions met
- dependency available
- context eligible
- not deprecated
- supported by current runtime policy

### Selection Philosophy

- minimum effective module set
- maximum research quality
- minimum context consumption
- maximum explainability

## 17. Dynamic Framework Selection

### Purpose

Determine the analytical frameworks required for the research plan.

Frameworks are discovered dynamically through the Framework Registry.

No framework is permanently attached to any task.

### Selection Criteria

- task type
- industry
- research mode
- research depth
- evidence available
- required analysis
- investment style
- decision complexity

### Framework Discovery

```text
Execution Plan
↓
Framework Registry
↓
Candidate Frameworks
↓
Compatibility Filter
↓
Priority Ranking
↓
Framework Stack
```

### Framework Categories

- Valuation
- Business Analysis
- Financial Analysis
- Technical Analysis
- Risk
- Macro
- Portfolio
- Decision
- Governance
- Statistical

Frameworks remain independent of Skill Packs.

## 18. Module Priority Engine

Every selected module receives a priority.

Priority levels:

- Critical
- High
- Medium
- Low
- Optional

### Priority Factors

- task importance
- dependency count
- expected impact
- research coverage
- execution cost
- context cost
- evidence contribution

The Execution Engine uses priority for scheduling.

## 19. Framework Priority Engine

Each framework receives one of the following priorities:

- Critical
- Primary
- Supporting
- Optional

Priority depends upon:

- materiality
- research depth
- expected decision impact
- framework dependencies
- context cost

Optional frameworks are removed first during optimization.

## 20. Dependency-Aware Planning

Every candidate module undergoes dependency analysis.

The Intelligence Engine never resolves dependencies on its own.

It requests dependency validation from the Dependency Map.

```text
Candidate Module
↓
Dependency Map
↓
Required Dependencies
↓
Dependency Status
↓
Planning Decision
```

Missing mandatory dependencies reduce module eligibility.

## 21. Registry Compatibility

Before approval verify:

- Module Registry Version
- Framework Registry Version
- Dependency Map Version
- Minimum Compatible Version
- Maximum Compatible Version
- Deprecated Status
- Compatibility Status

Only compatible modules enter the Research Plan.

## 22. Module Confidence Engine

Planning confidence differs from research confidence.

Planning confidence indicates confidence that a selected module belongs in the execution plan.

Confidence levels:

- Required
- Recommended
- Supporting
- Optional
- Experimental

Planning confidence is determined using:

- historical effectiveness
- task relevance
- dependency stability
- registry status
- execution history

## 23. Execution Strategy Selection

The Intelligence Engine determines how execution should occur.

Supported strategies:

- Sequential
- Parallel
- Hybrid
- Progressive
- Lazy Loading
- Fast Path
- Adaptive

### Strategy Selection Factors

- dependency graph
- research depth
- context budget
- module count
- execution cost
- evidence availability
- time sensitivity

Execution strategy becomes part of the ResearchPlanObject.

## 24. Dynamic Replanning

Planning may change during execution.

Triggers include:

- new evidence
- objective change
- module failure
- dependency failure
- context limit
- research conflict
- execution restart
- registry update

Only affected portions of the plan are rebuilt.

Complete replanning occurs only when necessary.

## 25. Planning Optimization

Before approval, optimize the plan by:

- removing duplicate modules
- merging overlapping capabilities
- reducing unnecessary frameworks
- minimizing context cost
- increasing evidence coverage
- improving explainability
- preserving institutional quality

Optimization must never reduce research quality.

# PART 5 — GOVERNANCE, VALIDATION & INTELLIGENCE LIFECYCLE

## 34. Intelligence Governance

Ensure every planning decision is transparent, explainable, auditable, and compliant with the AI Operating System.

The Intelligence Engine governs planning only.

Execution governance belongs to the Execution Engine.

Research governance belongs to the Research Engine.

Quality governance belongs to the Quality Audit Engine.

### Governance Principles

Every planning decision must be:

- explainable
- traceable
- repeatable
- evidence-aware
- registry-driven
- dependency-aware
- compatible
- institutionally rigorous

No planning decision shall rely upon undocumented assumptions.

## 35. Planning Failure Management

Planning failures may occur when:

- intent cannot be resolved
- task cannot be classified
- no compatible modules exist
- required frameworks are unavailable
- dependency validation fails
- registry incompatibility exists
- planning cost exceeds allowable limits
- research objective is ambiguous

### Failure Response

```text
Attempt intelligent replanning
↓
Reduce optional planning components
↓
Request alternative compatible modules
↓
Simplify planning strategy
↓
Generate planning warning
↓
Terminate planning gracefully if unresolved
```

The Intelligence Engine never forces invalid plans.

## 36. Intelligence Audit

Before releasing the ResearchPlanObject perform an internal planning audit.

Verify:

- correct intent identified
- correct task classification
- appropriate research mode
- appropriate research depth
- compatible modules selected
- compatible frameworks selected
- dependency validation completed
- registry compatibility verified
- planning costs estimated
- deliverables identified
- no unnecessary modules selected
- no duplicate frameworks selected

The audit validates planning quality only.

## 37. Intelligence Performance Monitoring

Monitor planning performance continuously.

Metrics include:

- Planning Duration
- Planning Accuracy
- Module Selection Accuracy
- Framework Selection Accuracy
- Dependency Resolution Success
- Planning Optimization Events
- Registry Query Efficiency
- Estimated vs Actual Runtime Accuracy
- Estimated vs Actual Context Usage

Performance metrics improve future planning but never alter completed sessions.
